# 智慧倉儲動態管理系統 2.0 - 今日修改重點及系統功能介紹

本文件記錄了今日（2026年5月7日）系統針對大數據量匯入與前端效能的關鍵優化，並總結了與匯入機制相關的系統功能行為，以供未來開發與維護參考。

## 一、 今日修改重點 (效能優化與 Bug 修復)

今日的修改主要集中在解決系統處理 6,000+ 筆大數據時所遭遇的崩潰與卡頓問題。

### 1. 解決 413 Payload Too Large 錯誤
* **問題**：當匯入超過 6,000 筆資料時，前端發送的 JSON 請求體積過大，超過 Express 預設的 100kb 限制，導致伺服器回傳 `413 Payload Too Large`。
* **解法**：在 `server/server.js` 中調整了 Express 中介軟體的設定，將 `express.json()` 與 `express.urlencoded()` 的上限提高至 `50mb`。

### 2. 解決大批量匯入 Timeout 與資料庫卡死
* **問題**：原先的匯入邏輯會將 Excel 內所有的料件條碼組成陣列，並使用 SQLite 的 `NOT IN (?, ?, ...)` 語法來刪除舊資料。由於 SQLite 對於單次 Query 的變數數量有嚴格上限，當資料量達到數千筆時會導致解析器崩潰或引發 `ERR_CONNECTION_TIMED_OUT`。
* **解法**：將過濾邏輯從 SQL 轉移至後端 JavaScript 記憶體中處理。改用 `Set` 資料結構比對資料庫現有條碼與 Excel 匯入條碼，精準找出需刪除的廢棄項目後再分批進行資料庫 `DELETE` 操作，大幅提升穩定性與執行速度。

### 3. 前端大數據列表渲染卡頓 (Lag) 解決方案
* **問題**：匯入 6,000 筆資料後，在「庫存查詢」、「庫存報表」與「出入庫紀錄」頁面，React 同時渲染數千個 DOM 節點導致瀏覽器嚴重卡頓。
* **解法**：全面實作 **前端分頁功能 (Client-side Pagination)**。目前將上述三個核心頁面統一設定為 **每頁顯示 100 筆**，並在表格下方加入分頁控制按鈕。當切換標籤或重新搜尋時，會自動重置回第一頁，徹底解決了操作卡頓問題。

### 4. 修復「主件主檔」匯入 500 報錯
* **問題**：如果上傳的「主件匯入範本.xlsx」中，不小心出現了重複的「主件品號 + 元件品號」組合，寫入資料庫時會觸發 `UNIQUE constraint failed`，導致伺服器報錯 `500 Internal Server Error` 且匯入中斷。另外，舊有邏輯並未達到「完全覆蓋」的標準。
* **解法**：修改 `/api/admin/import/bom` API。
  1. 匯入前先強制執行 `DELETE FROM bom_items` 進行完全清空。
  2. 使用 `ON CONFLICT(main_barcode, component_barcode) DO UPDATE` 語法，即使 Excel 有重複的組合，資料庫也能自動覆蓋過濾，不再報錯崩潰。

## 二、 系統功能介紹：大數據匯入機制說明

為確保工廠實務上的盤點與資料更新順利，目前系統的 Excel 匯入機制設計如下：

### 1. 料件主檔與主件主檔匯入 (完全覆蓋模式)
這兩項功能的定位是「建立標準資料」。
* 每次上傳新的 Excel 範本，系統會以**完全覆蓋** (Overwrite) 為原則。
* **料件主檔**：會保留並更新有出現在 Excel 裡的料件；**沒有出現在 Excel 裡的舊料件，將會被系統自動刪除** (包含其關聯的零庫存紀錄)。
* **主件主檔**：匯入時會**直接清空**整個 BOM 表，並完全以這次上傳的 Excel 內容重新建立 BOM 關聯結構。

### 2. 盤點庫存匯入 (防呆與更新模式)
盤點庫存的定位是「現場庫存狀態校正」。
* **清空與重建**：匯入盤點表時，系統會先清空目前的庫存表 (`inventory`)，然後依據 Excel 的內容重新建立庫存。
* **防呆機制 (防重複)**：如果在同一個 Excel 檔案中，同一項料件在同一個儲位出現了兩次 (重複資料)，系統具有防呆機制，會自動採取 **UPDATE (更新數量)** 覆蓋掉前一筆，而不會造成系統崩潰。
* **略過無效資料**：如果 Excel 中有資料**沒有填入「儲位代碼」**，或者填寫了系統中不存在的無效儲位，系統會**自動略過 (忽略)** 該筆資料不予匯入，以免資料庫產生沒有實際位置的幽靈庫存。

### 3. 操作建議與注意事項
* 在每次進行大批量匯入前，確保伺服器記憶體充足，且強烈建議先匯入「料件主檔」，再匯入「盤點庫存」與「主件主檔」，以確保關聯結構正常。
* 未來若資料量擴充至 10 萬筆等級，前端分頁仍能順利運作，但可能需要將後端的 Express `50mb` 限制進一步調高，或改採資料流 (Stream) 形式進行分批解析處理。
